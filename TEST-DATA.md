# Демонстрационные данные и что ими проверять

Файл описывает набор данных, который создаёт `frontend/workflow-ui/scripts/seed.mjs`, и что именно
можно проверить на каждом элементе. Данные покрывают роли, маршрутизацию, SLA с эскалацией,
переназначение, отмену, подпроцессы и журнал событий.

## Как получить данные

Стек должен быть запущен (см. «Running locally» в `README.md`), после чего:

```bash
cd frontend/workflow-ui
npm install
npm run seed
```

Скрипт идемпотентный: повторный запуск не дублирует записи, а пропускает уже существующие.
Он создаёт данные от имени разных пользователей (`admin1`, `coordinator1`, `manager1`), поэтому в
журнале событий видны реальные авторы действий.

Полный сброс: `docker compose down -v && docker compose up -d` и снова `npm run seed`.

Открыть UI: <http://localhost:5173>. Если реестр процессов пуст, а seed ещё не запускали — это
ожидаемо: модуль поставляется без данных. Если же вместо пустого списка вверху появилось красное
сообщение «сервис недоступен», значит не запущен `workflow-service` (см. раздел про запуск в
`README.md`).

## Учётные записи

Вход выполняется на собственной странице приложения: форма отправляет логин и пароль в Keycloak и
получает токен (никакого редиректа на страницу Keycloak не происходит, адрес остаётся
`http://localhost:5173`). Сессия хранится в `sessionStorage` — переживает перезагрузку страницы, но
не закрытие вкладки. Кнопка «Выйти» в меню профиля завершает сессию.

Все пароли — демонстрационные, из `infra/keycloak/realm-export.json`.

| Пользователь   | Пароль           | Роль        | Что доступно в UI |
|----------------|------------------|-------------|-------------------|
| `admin1`       | `admin123`       | ADMIN       | Всё: Процессы, Задачи, Шаблоны процессов, SLA политики |
| `manager1`     | `manager123`     | MANAGER     | Процессы, Задачи (в т.ч. переназначение), запуск и отмена процессов |
| `coordinator1` | `coordinator123` | COORDINATOR | Процессы, Задачи (выполнение), запуск и отмена процессов. Переназначения нет |
| `analyst1`     | `analyst123`     | ANALYST     | Только Процессы: реестр и карточка процесса, без действий |

## SLA-политики

| Код | Окно | Календарь | Эскалации | Что проверяет |
|-----|------|-----------|-----------|---------------|
| `DEMO_SLA` | 480 мин | Только рабочие часы | 80% → MANAGER | Базовый расчёт срока по рабочему календарю (срок сдвигается на рабочее время) |
| `DEMO_SLA_FAST` | 5 мин | Круглосуточно | 40% → MANAGER, 80% → ADMIN | Живая эскалация и нарушение SLA: всё происходит за 5 минут |
| `DEMO_SLA_24H` | 1440 мин | Круглосуточно | нет | Политика без эскалаций (список правил пустой) |

## Шаблоны процессов

| Код | Статус | SLA | Правила маршрутизации (по приоритету) | Что проверяет |
|-----|--------|-----|----------------------------------------|---------------|
| `DEMO_EXPERTISE_REVIEW` | Опубликован | `DEMO_SLA` | 0: `requestType == COMPLEX` → **EXPERT_REVIEW** / COORDINATOR | Базовый сценарий: простое условие, одна ветка |
| `DEMO_MULTI_ROUTE` | Опубликован | `DEMO_SLA` | 10: `amount >= 1000000` **AND** `region IN [MSK, SPB]` → **HEAD_REVIEW** / MANAGER<br>20: `requestType == SIMPLE` → **AUTO_CHECK** / ANALYST<br>30: правило-заглушка → **STANDARD_REVIEW** / COORDINATOR | Группа AND, операторы GTE и IN, порядок приоритетов («первое подошедшее выигрывает»), ветка по умолчанию |
| `DEMO_URGENT` | Опубликован | `DEMO_SLA_FAST` | 0: `priority == HIGH` → **URGENT_REVIEW** / COORDINATOR | Шаблон для наблюдения за эскалацией и просрочкой |
| `DEMO_SUBPROCESS_CHECK` | Опубликован | `DEMO_SLA_24H` | 0: правило-заглушка → **DOCUMENT_CHECK** / ANALYST | Шаблон, который запускается как подпроцесс |
| `DEMO_DRAFT_NO_RULES` | **Черновик**, правил нет | нет | — | Проверка валидации: публикация без правил маршрутизации должна быть отклонена |

Правило-заглушка — это условие `{"type":"condition","field":"__fallback__","op":"EXISTS","value":false}`:
поля `__fallback__` в атрибутах никогда нет, поэтому проверка «поле отсутствует» всегда истинна.

## Заявки (экземпляры процессов)

| Бизнес-ключ | Шаблон | Атрибуты | Состояние | Текущая задача | Что проверять |
|-------------|--------|----------|-----------|----------------|---------------|
| `REQ-2026-001` | `DEMO_EXPERTISE_REVIEW` | `requestType=COMPLEX` | Выполняется | EXPERT_REVIEW / COORDINATOR | Основной сценарий: выполнить задачу под `coordinator1` → процесс переходит в «Завершён», в журнале появляются TaskCompleted и ProcessStateChanged |
| `REQ-2026-002` | `DEMO_MULTI_ROUTE` | `amount=2500000, region=MSK, requestType=COMPLEX` | Выполняется | HEAD_REVIEW / MANAGER | Сработала ветка с группой AND (сумма ≥ 1 млн и регион из списка), хотя `requestType=COMPLEX`. У заявки есть подпроцесс |
| `REQ-2026-002-SUB` | `DEMO_SUBPROCESS_CHECK` | — | Выполняется | DOCUMENT_CHECK / ANALYST | Подпроцесс: в его карточке есть кнопка «Родительский процесс», ведущая на `REQ-2026-002` |
| `REQ-2026-003` | `DEMO_MULTI_ROUTE` | `requestType=SIMPLE, amount=5000, region=MSK` | Выполняется | AUTO_CHECK / ANALYST | Приоритеты: первое правило не подошло по сумме, сработало второе |
| `REQ-2026-004` | `DEMO_MULTI_ROUTE` | `amount=900000, region=NSK` | Выполняется | STANDARD_REVIEW / COORDINATOR | Ветка по умолчанию: не подошло ни первое (сумма и регион), ни второе (тип) правило. Запущена под `manager1` — в журнале виден другой автор |
| `REQ-2026-005` | `DEMO_EXPERTISE_REVIEW` | `requestType=COMPLEX` | **Завершён** | — | Полный журнал уже пройденного процесса: ProcessStarted → TaskCreated → TaskCompleted → ProcessStateChanged |
| `REQ-2026-006` | `DEMO_MULTI_ROUTE` | `amount=3000000, region=SPB` | Выполняется | HEAD_REVIEW, исполнитель `analyst1` | Переназначение с обязательной причиной: в списке задач вместо роли указан конкретный исполнитель, в журнале есть TaskReassigned с причиной |
| `REQ-2026-007` | `DEMO_EXPERTISE_REVIEW` | `requestType=COMPLEX` | **Отменён** | — (см. особенность ниже) | Отмена процесса с причиной, статус «Отменён», карта процесса скрыта |
| `REQ-2026-008` | `DEMO_URGENT` | `priority=HIGH` | Выполняется | URGENT_REVIEW / COORDINATOR → MANAGER → ADMIN | **SLA в динамике**: срок 5 минут. Через ~2 мин задача эскалируется на MANAGER, через ~4 мин — на ADMIN, через 5 мин статус становится «Просрочена». Фоновый планировщик опрашивает раз в 30 секунд |

`REQ-2026-008` имеет смысл смотреть сразу после `npm run seed` — эскалации проходят за пять минут,
дальше задача просто остаётся просроченной. Чтобы прогнать сценарий заново, запустите новый процесс
по шаблону `DEMO_URGENT` с атрибутами `{"priority":"HIGH"}`.

## Сценарии по ролям

### ANALYST (`analyst1`) — только чтение

1. В меню видны **только «Процессы»**: пунктов «Задачи», «Шаблоны процессов», «SLA политики» нет.
2. Прямой переход на `http://localhost:5173/tasks`, `/templates`, `/sla-policies` показывает
   «У вас нет прав для просмотра этой страницы».
3. В реестре процессов нет кнопки «Запустить процесс», в карточке — кнопки «Отменить процесс».
4. Карточка `REQ-2026-005` открывается и показывает журнал событий — чтение доступно.

### COORDINATOR (`coordinator1`) — работа с задачами

1. «Процессы» → «Запустить процесс»: доступны только опубликованные шаблоны, `DEMO_DRAFT_NO_RULES`
   в списке нет.
2. «Задачи»: фильтр по статусу, кнопка «Выполнить» есть, кнопки «Переназначить» **нет**.
3. Выполнить задачу заявки `REQ-2026-001` → процесс переходит в «Завершён» (следующее правило не
   подходит, потому что при выполнении атрибуты не передаются).
4. Отменить `REQ-2026-003` из карточки процесса с указанием причины.

### MANAGER (`manager1`) — переназначение

1. «Задачи» → у активных задач появляется кнопка «Переназначить».
2. Кнопка «Подтвердить» в диалоге заблокирована, пока не заполнены исполнитель **и** причина —
   причина обязательна по требованию REQ-02-007.
3. После переназначения задачи `REQ-2026-002` (HEAD_REVIEW) в карточке процесса в журнале
   появляется событие TaskReassigned с причиной и автором.

### ADMIN (`admin1`) — шаблоны и SLA

1. «Шаблоны процессов» → поиск по коду `DEMO_MULTI_ROUTE` → видны три правила с приоритетами;
   у первого — группа AND, её можно посмотреть в визуальном конструкторе и в сыром JSON.
2. Поиск по коду `DEMO_DRAFT_NO_RULES` → черновик без правил. Попытка опубликовать возвращает
   ошибку — публикация требует хотя бы одного правила маршрутизации.
3. Добавить правило в черновик и опубликовать → шаблон появляется в списке при запуске процесса.
4. «SLA политики» → три политики, у `DEMO_SLA_FAST` видны два шага эскалации.

## Негативные проверки

| Действие | Ожидаемый результат |
|----------|---------------------|
| Запуск процесса под `analyst1` (через API) | 403 Forbidden |
| Переназначение задачи под `coordinator1` (через API) | 403 Forbidden |
| Запуск `DEMO_EXPERTISE_REVIEW` с атрибутами `{"requestType":"SIMPLE"}` | 422: ни одно правило маршрутизации не подошло |
| Запуск процесса по черновику `DEMO_DRAFT_NO_RULES` | 409: шаблон не опубликован |
| Публикация `DEMO_DRAFT_NO_RULES` без правил | 409 |
| Повторное выполнение уже выполненной задачи (`REQ-2026-005`) | 409: недопустимый переход статуса |
| Переназначение без причины | 400: причина обязательна |
| Запрос без токена | 401 |
| Вход с неверным паролем | На форме появляется «Неверный логин или пароль.», страница не меняется |
| Вход при выключенном Keycloak | «Не удалось связаться с сервером авторизации…» |

Пример проверки через API (получение токена и запрос):

```bash
TOKEN=$(curl -s -X POST http://localhost:8081/realms/workflow/protocol/openid-connect/token \
  -d grant_type=password -d client_id=workflow-ui \
  -d username=analyst1 -d password=analyst123 | jq -r .access_token)

curl -i -X POST http://localhost:8090/api/process-instances \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"processDefinitionId":"00000000-0000-0000-0000-000000000000","businessKey":"X"}'
# ожидается 403
```

## Журнал событий и доменные события

- Журнал процесса виден в карточке заявки (раздел «История событий») и через
  `GET /api/process-instances/{id}/events`. Типы: `ProcessStarted`, `TaskCreated`, `TaskCompleted`,
  `TaskReassigned`, `ProcessStateChanged`, `SlaBreached`, `SlaEscalated`.
- Те же события уходят в Kafka через транзакционный outbox — топики `workflow.process.events`,
  `workflow.task.events`, `workflow.sla.events`. Посмотреть можно так:

```bash
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:19092 --topic workflow.task.events --from-beginning
```

- Входящая интеграция: сообщение `RequestAccepted` в топик `request.request-accepted` запускает
  процесс автоматически (см. `RequestAcceptedListener`). Пример конверта — в
  `RequestAcceptedListenerIntegrationTest`.

## Особенности, о которых стоит знать при тестировании

- **Отмена процесса не отменяет его задачи.** У `REQ-2026-007` статус процесса «Отменён», но задача
  EXPERT_REVIEW остаётся в статусе «Создана» и видна в реестре задач. Попытка её выполнить вернёт
  409, потому что отменённый процесс уже нельзя перевести в «Завершён».
- **При выполнении задачи атрибуты не передаются из UI**, поэтому следующий шаг ищется по пустому
  контексту. В демо-шаблонах это означает: у `DEMO_EXPERTISE_REVIEW` процесс завершается, а у
  `DEMO_MULTI_ROUTE` срабатывает ветка по умолчанию и создаётся задача STANDARD_REVIEW.
- **SLA считается только для незавершённых задач**; после перевода задачи в «Просрочена» эскалации
  по ней больше не применяются.
- Рабочий календарь для `businessHoursOnly` — с 9:00 до 18:00 UTC по будням, поэтому срок у
  политики `DEMO_SLA` обычно приходится на следующий рабочий день.
