# Этап 2 — маршрутизация, SLA и события

Второй срез: правила маршрутизации становятся деревьями условий, у задач появляются сроки,
эскалация и просрочка, а всё, что происходит в модуле, попадает в журнал и уходит доменными
событиями в Kafka.

## Что добавилось к этапу 1

| Область | Что реализовано |
|---------|-----------------|
| Условия маршрутизации | Дерево `AND / OR / NOT` любой вложенности, операторы `IN`, `NOT_IN`, `CONTAINS`, `EXISTS` вдобавок к сравнениям; визуальный конструктор и режим сырого JSON в интерфейсе (REQ-02-003, REQ-02-004) |
| SLA | Политики SLA (длительность, «только рабочие часы», ступени эскалации), расчёт срока по производственному календарю, привязка политики к шаблону (REQ-02-005) |
| Эскалация и просрочка | Фоновый планировщик раз в 30 с переводит задачу в «Просрочена» и поднимает её на роль из ступени эскалации (REQ-02-006) |
| События | Транзакционный outbox → Kafka (`workflow.process.events`, `workflow.task.events`, `workflow.sla.events`), DLQ после исчерпания попыток, конверт события с общей схемой |
| Входящая интеграция | Слушатель `RequestAccepted` на топике `request.request-accepted` запускает процесс автоматически (REQ-02-001) |
| Уведомления | Намерения на уведомление в топик `workflow.notifications` (доставка — за пределами модуля) |
| Журналы | Журнал событий процесса и журнал изменений шаблона, оба пишет AOP-аспект в одной транзакции с самим изменением (TZ §10) |
| Интерфейс | Карточка процесса с историей событий и картой маршрута, экран SLA-политик, срок и подсветка просрочки в реестре задач, скрытие пунктов меню по ролям |

## Чего ещё нет (появится на этапе 3)

- Пауза и возобновление процесса, отмена с закрытием открытых задач, подпроцессы
- Переназначение задачи на человека или на очередь роли
- Модель видимости по организации и участию в деле
- Аналитика, выгрузки CSV, сохранённые представления, каталог шаблонов

## Запуск

```bash
# 1. инфраструктура (Postgres + Kafka + Keycloak)
docker compose up -d postgres kafka keycloak

# 2. бэкенд
cd backend/workflow-service
mvn -DskipTests package
java -jar target/workflow-service-1.0.0.jar --server.port=8090

# 3. фронтенд
cd frontend/workflow-ui
npm install
npm run dev      # http://localhost:5173
npm run seed     # SLA-политики, шаблоны и заявки
```

У каждого этапа своя схема базы, поэтому **перед переключением на другой этап уберите том**:
`docker compose down -v`.

## Тесты

```bash
cd backend/workflow-service && mvn verify     # 37 модульных + 8 интеграционных (Testcontainers: Postgres + Kafka)
cd frontend/workflow-ui && npm run build && npm run lint
cd frontend/workflow-ui && npm run e2e        # Playwright: нужен поднятый и засеянный стенд
```

Что проверяется дополнительно к этапу 1:

- **Модульные** — вычисление дерева условий (группы `AND`/`OR`, вложенный `NOT`, `IN`, `CONTAINS`,
  `EXISTS`, пустая группа), расчёт срока SLA по рабочему календарю с праздниками, выбор ступени
  эскалации, планировщик просрочки, схема конверта события.
- **Интеграционные** (Postgres + Kafka) — золотой путь с проверкой того, что событие действительно
  ушло в Kafka через outbox; запуск процесса входящим событием `RequestAccepted`; проверка реального
  JWT против issuer на WireMock; журнал изменений шаблона (`ProcessDefinitionCreated`,
  `RoutingRuleAdded`, `ProcessDefinitionPublished` с автором); журнал событий заявки; маршрутизация
  по сгруппированному условию и 422, когда группа не сошлась.
- **E2E** — золотой путь, SLA-политики на экране, срок у задачи и история событий в карточке,
  сборка правила из двух условий в визуальном конструкторе.
