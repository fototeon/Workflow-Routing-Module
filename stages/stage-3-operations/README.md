# Этап 3 — эксплуатация: операции, доступ, аналитика

Третий срез доводит модуль до требований ТЗ целиком: то, что нужно людям, которые с процессами
работают каждый день — пауза, отмена, подпроцессы, переназначение, — и то, что нужно тем, кто за
ними наблюдает: модель видимости, дашборд, выгрузки.

Это и есть итоговое состояние модуля; в корне репозитория лежит он же.

## Что добавилось к этапу 2

| Область | Что реализовано |
|---------|-----------------|
| Операции над процессом | Пауза и возобновление (на паузе часы SLA стоят, срок сдвигается на длину паузы), отмена с закрытием всех открытых задач, запуск подпроцесса со ссылкой на родителя (TZ §2, §5, REQ-02-009) |
| Переназначение | Задача переназначается либо на конкретного человека, либо в очередь роли — ровно одно из двух, причина обязательна, каждое переназначение попадает в журнал (REQ-02-007) |
| Модель доступа | Роли ADMIN/MANAGER/ANALYST видят всё; остальные — заявки, которые сами запустили, где указаны владельцем, где на них (или на их роль) есть задача, либо незавершённые заявки своей организации (TZ §10) |
| Аналитика | Дашборд: количество процессов и задач, распределения по статусам и шаблонам, доля соблюдения SLA, среднее время процесса; выгрузки CSV по текущим фильтрам (TZ §3, §9) |
| Каталог шаблонов | Список всех шаблонов со статусом, версией и числом правил, фильтры по статусу и по коду/названию; публикация недоступна, пока нет ни одного правила |
| Удобство работы | Массовое выполнение задач, сортировка реестров, сохранённые представления фильтров, понятные сообщения об ошибках вместо кодов ответа, возврат с недоступной роли страницы |

## Запуск

```bash
docker compose up -d --build          # весь стенд целиком
cd frontend/workflow-ui && npm run seed
```

Либо из исходников, как на предыдущих этапах:

```bash
docker compose up -d postgres kafka keycloak
cd backend/workflow-service && mvn -DskipTests package && java -jar target/workflow-service-1.0.0.jar --server.port=8090
cd frontend/workflow-ui && npm install && npm run dev
```

У каждого этапа своя схема базы, поэтому **перед переключением на другой этап уберите том**:
`docker compose down -v`.

Подробности — в README, TEST-DATA.md и TZ-COMPLIANCE.md в корне репозитория: демо-данные, сценарии
по ролям, ожидаемые коды ошибок и построчное соответствие ТЗ.

## Тесты

```bash
cd backend/workflow-service && mvn verify     # 39 модульных + 52 интеграционных
cd frontend/workflow-ui && npm run build && npm run lint
cd frontend/workflow-ui && npm run e2e        # Playwright, 14 сценариев
```

Что проверяется дополнительно к этапу 2:

- **Матрица прав** — 39 пар «роль × эндпоинт» плюс проверка, что без токена каждая защищённая
  область отвечает 401, и что OpenAPI описывает все публичные операции.
- **Возможности этапа** — пауза со сдвигом срока, отмена с закрытием задач, журнал изменений
  шаблона, подпроцесс со ссылкой на родителя, переназначение на человека и в очередь роли, дашборд
  и выгрузка CSV аналитиком, видимость заявок для координатора, каталог шаблонов с правилами
  публикации.
- **E2E** — 14 сценариев: золотой путь, переназначение с обязательной причиной, ограничения по
  ролям, пауза и возобновление, подпроцесс и возврат к родителю, карта маршрута, массовое
  выполнение, дашборд аналитика с выгрузкой, сохранённые представления, смена учётной записи и
  каталог шаблонов.
